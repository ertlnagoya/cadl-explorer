# Violation Timeline による課題Ａ（A1〜A3）の進め方

CADL Explorer v1.9.2 以降 · 卒業研究計画書（案）「SoS契約の違反を可視化し改善案を提示する設計支援システム」の課題Ａに対応

## (1) この説明書の範囲

本書は，CADL Explorer の Violation Timeline のページを使って，卒業研究計画書（以下，計画書）の課題Ａ（A1 違反の記録，A2 違反の可視化，A3 改善提案）を進める手順を示す。計画書の(5)「課題Ａの評価方法」の項目ごとに，どのタブで何を操作し，何を記録として残すかを対応づけて書く。

ページが行うことは次の三つである。

1. ランタイムが報告した違反（契約インスタンスごとに最初の1件）を，継続評価の記録および注入した故障（正解）と並べて，時間の流れとして表示する（A2）。
2. 多数の試行から，記録の再現率，原因一致率，マスキング発生率を，95%の信頼区間とともに求める（A1）。
3. 原因の候補から契約パラメータの変更案を作り，同じ試行を再実行して適用前後を比べる（A3）。

ページは，SoS-DSL の参照ランタイム（raspimouse-swarm-simulator の `cadl/runtime/engine.py`）を変更せず，複製もしない。継続評価は，違反の遷移をとらないランタイムの派生クラスを，もとのランタイムと同じシナリオで並行して動かして記録する。これは計画書の(8)のリスク表にある「別の評価器を並行して動かし，ログを突き合わせる方式」にあたる。ランタイム自身が継続評価を記録するように改修された後は，そのログを同じページで読める（(4)の形式に合わせる）。

CADL Explorer の中での位置付け

CADL Explorer のページは，設計の段階ごとにナビゲーションの節に分けている。Violation Timeline は「動かして確かめる」の節にあり，Designer で書いて静的に検証した契約を，故障を注入して動かし，監視の報告が原因を正しく指すかを確かめる段階を受け持つ。確かめる対象はロボットや実装の誤りより，契約の監視の書き方（期限，監視周期，監視の数）である。

| 節 | ページ | 確かめること |
| --- | --- | --- |
| 探る | Explorer | 制度の選択肢（D-SoS と C-SoS など）を比べ，その違いが振る舞いにどう伝わるか |
| 設計する | Designer | 契約，ライフサイクル，監視を書き，読み返し，矛盾がないかを検査する（norms-check，game-check）。版を残し，改正する |
| 動かして確かめる | Violation Timeline，Contract Lifecycle | 故障を注入して動かしたとき，ランタイムの報告が故障を正しく指すか。ランタイムが動かす IR のライフサイクル |
| 記録する | Decision Evidence | 設計を変えた理由と，その根拠とした計測値 |

動かして確かめる機能は，Designer の **確かめる** の段階にもある。Traces（`cadl norms-eval`）は記録した実行で規範が守られたかを，計測（`cadl metrics-eval`）は計測値が目標を満たしたかを，エージェント（`cadl agents-run`）はエージェントの境界での判定を確かめる。Violation Timeline は，同じ種類の実行記録から，監視の報告が正しいかを判定する。ページの上部のボタンで，Designer のこれらのビューに移れる。

設計との往復は次のとおりである。

1. Designer の **確かめる** › まとめ，ないしは **書き出す** の「この設計を Violation Timeline で開く」で，その設計の IR を読み込んだ状態でこのページに移る。
2. **改善提案** で選んだ変更は，「選んだ変更を Designer に提案する」で Designer の **変える** の段階に送る。Designer は変更後の設計を検査し，新しく出る問題を示す。
3. 判断の理由を書いて「提案を適用する」を押すと，変更前の設計が版として残り，判断が判断の記録に入る。ソースは変わる行だけを書き換えるので，コメントは残る。その行が見つからない場合は設計全体を書き直すのでコメントは残らず，Designer はそのことを示す。`# @amend:` の印のある値は，この方法では変えない。憲法が単位，範囲，刻みを決めているので，「改正できるパラメータ」で改正する。
4. 判断の記録の「Decision Evidence で開く」で，その記録を `cadl decisions-verify` の検査とともに見られる。判断の記録は，decisions.jsonl（付録L）と各版の CADL ファイルとしてダウンロードできる。

運用段階でも，ランタイムが継続評価を記録していれば，報告された違反ごとに原因の候補を示せる。ただし運用段階には正解がないので，A1 と A3 の指標は求められない。運用段階での使い方は，責任の帰属（修士研究の候補）と合わせて扱う。

## (2) 準備

アプリの起動

リポジトリの直下で，参照ランタイムの場所を環境変数 `CADL_RUNTIME_PATH` に与えて起動する。

```bash
CADL_RUNTIME_PATH=~/program/raspimouse-swarm-simulator .venv/bin/streamlit run app.py
```

環境変数を与えずに起動した場合も，**実行** のタブの「ランタイムの場所」に同じパスを入力すればよい。ランタイムが見つかると，その場所が緑の枠で表示される。ランタイムがない環境（公開版のアプリなど）では，ログの表示，計測，改善提案の一覧は使えるが，実行と再実行はできない。

ページの開き方

左のナビゲーションで **Violation Timeline** を選ぶ。言語の切り替えはサイドバーの上端にある。

入力の選び方（サイドバー）

| 項目 | 内容 |
| --- | --- |
| シミュレータの IR | 同梱の例（`sos_dsl_robot_delivery.ir.json`），アップロードした `cadl sim-ir --format json` の出力，Designer で開いている設計のいずれか |
| NDJSON のログ | ランタイムのログ（複数可）。アップロードしたログは「表示するログ」の一覧に加わる |
| 正解（任意） | 注入した故障を別のファイルで与える場合に使う（(4)を参照） |
| 表示するログ | 同梱のログ，アップロードしたログ，このページで実行したログから一つ選ぶ |
| 原因の候補 | 「成立が最も早い」と「記録が最も早い」の二つの規則を切り替える（(5)のA1-3を参照） |

同梱のログは次の四つである。いずれも参照ランタイムで作ったもので，作り方は `cadl_sim/sos_dsl/examples/violations/README.md` にある。

| ファイル | 内容 |
| --- | --- |
| `demo_accept_5s.ndjson` | `multi_robot_demo` のシナリオをそのまま実行したもの |
| `demo_accept_1s.ndjson` | `accept` の期限を1sにしたもの（個別演習と同じ設定） |
| `demo_accept_300ms.ndjson` | `accept` の期限を300msにしたもの。robot-2-1 で計画書の図1と同じマスキングが起きる |
| `batch_example.ndjson` | baseline のシナリオで40試行を一括実行したもの（`accept` の期限 500/5000ms × Assigned の滞在時間 100/700ms × 故障2種類 × 5回） |

最初に `demo_accept_300ms.ndjson` を表示し，タイムラインで robot-2-1 の上の帯（報告）に `deadline:accept`，下の帯（継続評価）に `battery_guard` の印が出ることを確かめる。ページを開いたときに表示されるのも，このログである。

## (3) ページの構成

上部の四つの数字は，表示中のログの試行数，インスタンス数，マスキングのあるインスタンス数，原因を取り違えた報告の数である。後の二つは，それぞれ継続評価の記録と正解がログにある場合にだけ数える。

| タブ | 計画書の課題 | 主な表示と操作 |
| --- | --- | --- |
| 実行 | A1，A3 | 1回の実行，一括，ログのダウンロード |
| 時系列 | A2 | 状態の帯（報告と継続評価の2段），違反と故障の印，インスタンスの表，ライフサイクルの図 |
| 計測 | A1 | 条件ごとの指標の表とグラフ，取り違えの理由の集計，故障を注入したインスタンスの一覧 |
| 改善提案 | A3 | 契約の変更案（適用の選択），前提（assume）の案，再実行と比較，Designer への提案 |

タブは作業の順に並ぶ。以下，**時系列** のタブの帯と印の表示を「タイムライン」と呼ぶ。ページを開いたときは，表示中のログの **時系列** が選ばれている。

タイムラインの読み方

各インスタンスに2段の帯がある。上の段（「報告」）はランタイムが報告した状態，下の段（「継続評価」）は違反の状態に入らなかったと仮定した状態（仮定状態）である。印は次の3種類である。

| 印 | 意味 | 置かれる段 |
| --- | --- | --- |
| 黒の十字 | 報告された違反 | 報告 |
| 橙の丸 | 報告されなかった違反（継続評価でのみ記録） | 継続評価 |
| 赤紫の下向き三角 | 注入した故障（正解） | 報告の段の上端 |

周期的な監視の印の前にある破線は，その監視の条件が成立し始めた可能性のある範囲である。周期的な監視は評価の時点でしか条件を見ないので，記録された時刻は成立の時刻から最大で1周期遅れる。例えば `battery_guard`（周期500ms）が550msに記録された場合，条件は50msより後，550ms以前に成立している。時刻の範囲は「時刻（ms）」のスライダで狭められる。

## (4) ログの形式

ページはランタイムの NDJSON のログをそのまま読む。ランタイムが現在出力する記録（`kind` が `lifecycle` と `violation`）だけのログは，報告として表示する。課題Ａに必要な情報は，次の任意の項目として加える。これらはすべて既存の記録に項目を足すか，新しい `kind` の記録を足すもので，既存の項目の意味は変えない。

| 追加 | 形式 | 用途 |
| --- | --- | --- |
| 継続評価 | `lifecycle` と `violation` の記録に `"track": "continued"` を付ける | 仮定状態の帯，報告されなかった違反 |
| 注入した故障 | `{"kind": "injection", "instance_id", "t_ms", "fault", "params", "expected"}` | 正解。評価にのみ用いる |
| 実行の条件 | `{"kind": "run", "trial", "scenario", "condition", "ir_overrides", "params", "injections", "end_ms"}` | 条件ごとの集計（A1），再実行（A3） |
| 試行の番号 | 任意の記録に `"trial"` を付ける | 1ファイルに複数の試行を入れる |

継続評価の違反は，インスタンスごと，`detected_by` ごとに，最初に成立した1件だけを記録する。`expected` は，その故障を正しく指す `detected_by` の一覧である。省略した場合は次の既定の対応を使う。

| `fault` | 正しく指す違反 |
| --- | --- |
| `battery_drop` | `monitor:battery_guard` |
| `over_speed` | `monitor:over_speed` |
| `ack_missing`，`ack_delay` | `deadline:accept`（`params.transition` で変更可） |
| `delivery_stall` | `monitor:deadline_watch` |

正解をログとは別のファイルで与える場合は，`injection` の記録だけを並べた NDJSON をサイドバーの「正解（任意）」に与える。`trial` を付けた記録はその試行にだけ，付けない記録はすべての試行に加わる。故障を注入する側（ランタイムないしはシナリオ）の `truth()` の形式が決まった段階で，この形式との対応を確認する。

Unity の Console の出力は現在 NDJSON ではないので，そのままでは読めない。計画書(4)の3にあるとおり，Unity の出力を同じ形式にそろえた後で読み込む。

## (5) A1 違反の記録の進め方

計画書(5)のA1の4項目に対応させて進める。

A1-1 記録の正しさ

1. **実行** →「1回の実行」で，シナリオに「baseline（故障なし。下で注入）」を選び，注入の表を空のまま実行する。タイムラインのすべてのインスタンスが `Completed` で終わり，違反の印が一つもないことを確かめる。
2. **実行** →「一括」で，故障を1種類ずつ選び，`accept` の期限と周期は既定値のまま一括実行する。**計測** の「記録の再現率」が100%であることを確かめる。
3. 再現率が100%に満たない場合は，**計測** の「報告が故障を指さなかった理由」の表を見る。「監視の対象の状態で故障が続いた時間が，監視周期より短かった」ないしは「監視の対象の状態を出た後で故障が起きた」は，監視周期による見逃しである。「継続評価でも，故障を指す違反が記録されなかった」が残る場合は，実装の誤り（故障の注入，イベント名，IR の監視の式）を疑い，そのインスタンスをタイムラインで確かめる。

一括実行では，故障させるロボットと時刻を乱数で決める。`battery_drop` はそのロボットが ack を返すまでの間，`over_speed` は配送中，`ack_missing` と `ack_delay` は割り当ての時刻から有効になる。`ack_delay` の遅延が期限の内に収まる場合は，契約上は違反ではないので正解の違反を空とし，再現率と一致率の分母に含めない。

A1-2 マスキングの実測

1. **実行** →「一括」で，変える条件を入力する。`accept` の期限，`battery_guard` の周期，Assigned の滞在時間は，それぞれカンマで区切って複数の値を与えられ，そのすべての組み合わせについて，選んだ故障ごとに指定の回数だけ試行する。計画書の例に合わせて，回数は30とする（予備実験では5〜10で傾向を見る）。シードを記録しておけば，同じ試行を再現できる。
2. 実行が終わると，そのログが「表示するログ」に選ばれる。**計測** の表に，条件ごとの記録の再現率，原因一致率（報告），原因一致率（候補），マスキング発生率が「割合［95%区間］（k/n）」の形で並ぶ。区間は Wilson の方法による。下のグラフは同じ値を条件ごとに並べたものである。
3. 計画書の「マスキングが起きる条件の分類表」は，「報告が故障を指さなかった理由」の表から作る。理由は次の五つに分けている。

| 理由 | 意味 |
| --- | --- |
| `deadline_before_fault` | 故障の違反が検出される前に期限が切れた |
| `other_monitor_first` | 故障に対応する監視より先に，別の監視が成立した |
| `other_deadline_first` | 故障に対応する期限より先に，別の期限が切れた |
| `dwell_shorter_than_period` | 監視の対象の状態で故障が続いた時間が，監視周期より短かった |
| `fault_outside_watched_state` | 監視の対象の状態を出た後で故障が起きた |

4. **計測** の「表をダウンロード（CSV）」で指標の表を，**実行** の「表示中のログをダウンロード（NDJSON）」でログそのものを保存する。卒業論文の数値は，このログから再計算できるようにしておく。

同梱の `batch_example.ndjson` では，Assigned の滞在時間が100msの条件で `battery_drop` の記録の再現率が0/5となり，理由はすべて `dwell_shorter_than_period` である。これはハンズオン教材の「`Assigned` に留まる時間を監視周期より短くすると `battery_guard` が違反を検出できなくなる」という注意と一致する。

A1-3 原因の候補の比較

**計測** の「原因一致率（報告）」と「原因一致率（候補）」を同じ試行で比べる。原因の候補は，継続評価の記録だけから選び，正解を使わない。サイドバーの「原因の候補」で規則を切り替えられる。

| 規則 | 選び方 |
| --- | --- |
| 成立が最も早い（既定） | 条件が成立し始めた可能性のある時刻（周期的な監視では記録の1周期前）が最も早い違反 |
| 記録が最も早い | ログで最初に記録された違反 |

二つの違反の成立の範囲が重なる場合，ログからはどちらが先かを決められない。インスタンスの表では，その候補に「（監視周期の幅の中で順序は未確定）」と付ける。「成立が最も早い」の規則は，周期の長い監視を候補に選びやすい。両方の規則で原因一致率を求め，その差も結果として報告する。

A1-4 監視の数と原因の特定の関係

ページの一括実行で変えられる IR の値は，`accept` の期限と `battery_guard` の周期である。監視の数を変えるには，監視を1個，3個，5個と加えた CADL の設計をそれぞれ用意し，`cadl sim-ir --format json` で IR を作る（Designer で編集した設計は，サイドバーの「Designer の設計」でそのまま使える）。IR ごとに同じ条件と同じシードで一括実行し，ログを保存する。計測の表の条件の欄には IR の名前が入らないので，IR ごとのログを切り替えて表を並べるか，保存した CSV を一つにまとめて比べる。

加える監視の式は，シナリオが与える観測値（`ROBOT.battery`，`ROBOT.speed`，`request.deadline`，`now`，`state`）で書く。それ以外の値を参照する式は，参照ランタイムでは常に成立しない（関数呼び出しを含む `collision_watch` も同じ）。`over_speed` を加える場合は，速度の閾値をシナリオの速度（既定1.0）と注入する速度（既定3.0）の間に置く。監視を増やしても原因一致率が上がらない条件が見つからなかった場合も，その結果をそのまま報告する。

## (6) A2 違反の可視化の進め方

A2-1 表示の正しさ

帯と印の時刻と種類がログと一致することは，自動テスト `tests/test_violation_trace.py` の `test_timeline_chart_matches_the_log` で確かめている。このテストは，同梱のログのすべての `lifecycle` の記録について同じ時刻に始まる帯が，すべての `violation` と `injection` の記録について同じ時刻と種類の印が，図のデータにあることを検査する。次のコマンドで実行する（ランタイムを使う3件のテストは，`CADL_RUNTIME_PATH` があるときだけ実行される）。

```bash
CADL_RUNTIME_PATH=~/program/raspimouse-swarm-simulator .venv/bin/python -m pytest -q tests/test_violation_trace.py
```

事例に使うログを新しく作った場合は，そのログを `cadl_sim/sos_dsl/examples/violations/` に置き，このテストの `parametrize` の一覧にファイル名を加える。

A2-2 事例による評価

計画書が挙げる3件の事例を，次の手順で作る。各事例について，従来のサマリの表（`multi_robot_demo --summary` の出力，ないしはインスタンスの表の「報告された違反」の列だけ）で原因を説明できるかと，タイムラインの表示で説明できるかを対比して書く。

| 事例 | 作り方 | タイムラインで見る点 |
| --- | --- | --- |
| 個別演習の robot-2 と robot-3 の違反理由の入れ替わり | `demo_accept_5s.ndjson` と `demo_accept_1s.ndjson` を切り替えて表示する。Unity のログが NDJSON になった後は，同じ設定の Unity のログを読み込んで並べる | 報告の印と継続評価の印の時刻，破線の範囲 |
| 滞在時間が監視周期より短いことによる見逃し | 一括実行で Assigned の滞在時間を100msにし，`battery_drop` を選ぶ（`batch_example.ndjson` にも含まれる） | Assigned の帯の長さと，印がないこと。理由の欄 |
| 複数の故障の同時注入 | 「1回の実行」で baseline を選び，注入の表に同じロボットへの故障を2行（例えば `battery_drop` と `ack_missing`）入れる | 二つの故障の三角と，どちらの違反が報告されたか |

参照ランタイムのデモでは，`accept` の期限を1sにしても robot-2-1 の報告は `monitor:battery_guard`（550ms）のままで，`deadline:accept`（1100ms）は報告されない（マスキングされる）。個別演習で観測した入れ替わりは，Python のデモでは再現しない。Unity では割り当てから ack までの時間（`Assigned Dwell Ms`）や監視の評価の時刻が異なるため，その違いが入れ替わりを生んでいるかを，Unity のログを同じ形式で読み込んで確かめる必要がある。この確認の結果も事例の記述に含める。

各事例は，入力のファイル（IR とログ）と操作の手順を残し，第三者が再現できるようにする。ページで実行したログには `run` の記録があり，シナリオ，IR の変更，注入した故障，シードによる条件がすべて入っているので，ログを保存すれば再実行できる。

## (7) A3 改善提案の進め方

1. マスキングないしは原因の取り違えのあるログ（例えば `demo_accept_300ms.ndjson` や一括実行のログ）を表示し，**改善提案** を開く。
2. 「契約の変更案」の表に，規則ごとの案が並ぶ。各行に，規則，CADL のソースでの変更（例：`DELIVERY_SLA › lifecycle › accept: deadline: 300ms → deadline: 600ms`），案の対象となったインスタンスの数，最初の例の理由がある。規則は次のとおりで，いずれも原因の候補と IR だけを入力とし，正解を使わない。

| 規則 | 当てはまる条件 | 変更案 |
| --- | --- | --- |
| R1 | 期限の違反が報告されているが，原因の候補が別の違反である | 候補の記録の時刻まで期限を延ばす（100ms単位に切り上げ，100msの余裕を加える） |
| R2 | 周期的な監視の対象の状態の滞在時間が，監視周期より短い | 周期を最短の滞在時間まで短くする（50ms単位。滞在が50ms未満なら `sampling: event` を検討する旨を示す） |
| R3 | 監視の違反が報告されているが，原因の候補が別の周期的な監視である | 候補の監視の周期を半分にする |
| A1 | 原因の候補がロボットによる違反である | 契約の前提（assume）として，ロボットに守ることを求める条件を示す。IR は変更しない |

3. 計画書(5)のA3-1は提案規則ごとの評価を求めているので，「適用」の列で一つの規則の案だけを選んで再実行し，結果を記録してから次の規則に移る。複数の規則を組み合わせた効果は，その後で別に測る。
4. 「選んだ変更で同じ試行を再実行」を押すと，各試行の `run` の記録にあるシナリオ，故障（注入時刻と対象も同じ），もとの条件をそのまま使い，選んだ変更だけを加えて実行する。
5. 結果として，解消率，副作用率，提案の網羅率と，インスタンスごとの適用前後の表，選んだ試行の適用前後のタイムラインが表示される。

| 指標 | 定義 |
| --- | --- |
| 解消率 | 案の対象で原因を取り違えていたインスタンスのうち，変更後に注入した故障が報告された割合 |
| 副作用率 | 故障を注入していないインスタンスのうち，最終状態が変わった割合 |
| 提案の網羅率 | マスキングか原因の取り違えがあった試行のうち，提案を出せた割合 |

期限や閾値を緩めれば違反そのものが消えるので，違反の件数が減ったことは成功とみなさない（計画書(5)のA3-2）。解消率は，注入した故障を指す違反が報告されたかどうかで判定する。

6. 「提案を出せなかった試行」に並ぶ試行は，対応する規則がない条件である。タイムラインでその試行を開き，どの条件で取り違えが起きたかを確かめて，計画書の「提案規則の一覧」と「規則がない条件の一覧」に記録する。
7. 「選んだ変更を反映した IR をダウンロード」で，変更後の IR を保存できる。ランタイムがない環境では，この IR で自分でランタイムを実行し，そのログを「変更後のログ」に読み込めば，同じ比較が表示される。このとき，試行の番号（`trial`）を適用前のログと一致させる。

8. 採用する案は，「選んだ変更を Designer に提案する」で Designer の **変える** の段階に送る。Designer は，ソースの該当箇所（`lifecycle` の `deadline:`，`monitors` の `sampling:`）を書き換えた設計を検査して示す。判断の理由を書いて適用すると，変更前の設計が版として残り，判断と，再実行で測った解消率，副作用率，網羅率が判断の記録に入る。設計の値が，提案のもとになった実行の条件と違う場合（同梱のログは `accept` の期限を 300ms にして実行している）は，Designer が警告を出し，値を確かめたことの確認を求める。このボタンは，IR が Designer の設計のときだけ使える。同梱の IR やアップロードした IR では，変更を戻す設計がない。

## (8) 結果の残し方

卒業論文の数値と図を再現できるよう，実験ごとに次のものを残す。

| 残すもの | 入手のしかた |
| --- | --- |
| ログ（NDJSON） | **実行** の「表示中のログをダウンロード（NDJSON）」 |
| 使った IR | 同梱の IR の名前，ないしはアップロードした IR のファイル。変更後の IR は **改善提案** からダウンロード |
| 指標の表（CSV） | **計測** の「表をダウンロード（CSV）」 |
| 判断の記録 | Designer の **変える** の判断の記録から「decisions.jsonl としてダウンロード（.zip）」 |
| 条件 | 一括実行に入力した値，故障の種類，回数，シード（ログの `run` の記録にも残る） |
| ランタイムの版 | raspimouse-swarm-simulator のコミット（`git -C ~/program/raspimouse-swarm-simulator log -1 --oneline`） |
| Explorer の版 | サイドバーの下に表示される版 |

ページで実行したログは，ページを閉じると消える。必要なものはその場でダウンロードする。

## (9) 制約と注意

1. 継続評価は Explorer 側の派生クラスで記録している。ランタイム自身に継続評価を実装した後は，同じシナリオのログを両方で作り，継続評価の記録が一致するかを確かめる。報告側の記録は，`multi_robot_demo --log` の出力と1件ずつ一致することをテスト（`test_runner_report_equals_the_runtime_alone`）で確かめている。
2. 原因の候補の時刻は，周期的な監視では最大1周期の幅を持つ。候補の順序が決まらない場合は表に明示しているので，結果を述べるときもその件数を合わせて示す。
3. デモのシナリオの正解は，デモの説明に書かれた故障を記録したものである（robot-1-1 の ack なし，robot-2-1 のバッテリの急減，robot-3-1 の配送の遅延）。robot-2-1 も ack を返さないが，これは Assigned に留めるためのシナリオの仕掛けとみなし，故障に数えていない。この扱いは研究の中で決める事項であり，変える場合は正解のファイルを別に与える。
4. 実行のタブは契約 `DELIVERY_SLA` を前提としている。baseline のシナリオは，IR の遷移 `assign`，`accept`，`start_delivery`，`complete` の `on:` をイベント名として使う。これと異なる契約の IR では，表示と計測はできるが，実行はできない。
5. baseline のシナリオで画面から変えられるのは Assigned の滞在時間だけである。ロボットの台数，割り当ての間隔，配送時間を変える場合は，`cadl_sim/sos_dsl/runtime_runner.py` の `BaselineParams` を使う。
6. 課題Ｂ（観測の遅延，欠落，ジッタ）の注入は，このページにはない。故障の注入と同じ位置（シナリオとランタイムの間）に加える形を想定している。
